# 1.7.5 の変更内容

1.7.5 は DB2016、YBB、SBK、Native Book v4 の保存時間と一時メモリを改善する、後方互換な patch 更新である。
既存の公開 API、Cargo feature、外部依存、定跡と棋譜の保存形式は維持する。
Rust と Python の公開 API は追加しない。
既存利用者によるコードや定跡ファイルの移行作業は不要である。

持駒差を挟む履歴の千日手判定は、[1.7.4](release-1.7.4.md) で修正済みである。
1.7.5 にも累積して含まれるが、今回の新規変更は保存処理の改善であり、千日手判定を追加変更するものではない。

## DB2016 の保存

`YaneuraOuBook::write_yaneuraou_db2016_with_patch` と制御付き版は、reader が検証して正規化した元行を再利用する。
未変更行のために編集用の `BookDatabaseEntry` を作り直さず、SFEN の再解析と再生成、DB2016 出力では使わない PackedSfen の生成、候補とコメントの複製を省く。
元行の検査は削除対象と置換対象にも適用し、不正入力を差分で隠さない。

`BookDatabase::write_yaneuraou_db2016` は出力前の全件検証を維持し、事前検証のために全文字列化する処理を省いた。
数値と指し手も出力バッファへ直接整形し、一時文字列を減らす。
候補順、手数の省略と明示的な 0、コメント、オプション、進捗通知とキャンセルの契約は維持する。

## YBB の保存

`BookDatabase::write_ybb` は出力前に全入力を検証し、出力時は検証済みのキーと手数を再利用する。
出力段階での SFEN 解析、PackedSfen 生成、合法手の再検査を省き、候補の一時バッファを再利用する。
所有 IR と局面数に比例する整列索引は必要だが、全候補を変換済みデータとして保持しない。

`YbbBook::write_ybb_with_patch` と制御付き版は、変更行の変換結果を保持して再利用する。
変更数が多い場合の時間短縮と引き換えに、変更した局面と候補に比例する追加メモリを使う。
元全行の構造、符号化、キー順、一意性の検査と、追加行および置換行の合法手検査は維持する。
未変更行の局面復元や合法手検査を新たに行うものではない。

## SBK の保存

`BookDatabase::write_sbk` は全局面の `Position` を保持せず、候補を処理する局面だけを再解析する。
候補ごとの clone を apply/undo に置き換え、検査集合と符号化用バッファを再利用する。
全出力の Vec を作らず、内部ブロックへまとめて出力するため、呼出し側が File を直接渡しても細かい I/O を増やさない。

所有 IR とグラフ処理に必要な領域は残るため、一定メモリの保存 API ではない。
全バイト列が必要な場合の `to_sbk_bytes()` は、従来どおり Vec を返す。
全入力の検証、root 順と ID の再採番、子局面リンク、候補順、メタデータの扱いを維持する。
既存 SBK の差分保存では出力バッファを再利用し、グラフ検証と未知フィールドの保持は変更しない。

## Native Book v4 の保存と検証

中間 run では構造と符号化の検査を維持し、盤面と候補の意味検証を公開前の完成本体へ集約する。
入力時の検証、公開前の完全検証と原子的な公開は維持する。
builder の入力検証と reader の全件検証では作業用 Position を再利用し、局面ごとの履歴領域の確保と初期化を減らす。
builder の作業領域は Box で保持し、Python の所有オブジェクトへ Position の alignment を伝播させない。
正準形、候補の合法性、保存バイト列と公開 API は変更しない。

通常 release の 2,106万局面の consumer 試験では、検証集約で finish が 130.951 秒から 82.917 秒になった。
その後の Position 再利用の ABBA 各 2 回では finish 平均が 79.391 秒から 66.699 秒になり、全量出力は固定出力と全バイト一致した。
前者は各 1 回の比較で、後者の peta 全体の wall 平均はほぼ同等だった。
異なる比較の短縮率を合算せず、通常の探索や全環境での高速化は主張しない。

## 比較結果と適用範囲

20261031 配布の `book_miner-20260708065419_21067205.db` を使い、Windows、Ryzen 9 7950X、Rust 1.95.0、AVX2 有効の release ビルド、PGO なしで比較した。
保存時間は形式検証、整列またはグラフ処理、符号化、出力と flush を含む。
入力からの IR 構築と、終了後の `sync_all` は含まない。
各版を A/B/B/A の順で 2 回ずつ測った平均である。

| 保存 API | 局面数 | 改善前の秒 | 改善後の秒 |
|---|---:|---:|---:|
| DB2016 差分保存、変更なし | 21,067,205 | 261.54 | 142.82 |
| YBB 全件保存 | 1,000,000 | 11.67 | 8.79 |
| SBK 全件保存 | 300,000 | 17.35 | 6.34 |

SBK のピーク working set は約 6451 MiB から 327 MiB へ減った。
メモリは読込みと IR 構築を含むプロセス全体の OS 高水位カウンタを 20 ms ごとに取得した値であり、終了直前の短い区間を観測できない場合がある。

YBB の 100 万局面中 10 万局面を置換する保存は、平均 1.640 秒から 1.174 秒へ短縮した。
その一方、ピーク working set は約 228 MiB から 240 MiB へ増えた。
少量の差分と SBK 差分保存は実行間のばらつきがあり、大幅な速度改善を結論していない。

比較対象の出力は改善前後で全バイト一致した。
上表は各保存 API の条件を固定した比較であり、アプリケーション全体の短縮率ではない。
専有ホストでの計測ではなく、YBB と SBK は元定跡の先頭部分を使っているため、他のデータや環境でも同じ改善率になるとは保証しない。
Python にこれらの保存 API を追加したリリースではない。

各形式の検証範囲と保存時の契約は、[定跡アーキテクチャ](../reference/formats/book-architecture.md)、[DB2016 と YBB](../reference/formats/yaneuraou.md)、[SBK](../reference/formats/sbk.md) を参照する。
